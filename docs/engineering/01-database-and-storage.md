# 1. Database and storage

Status: full target schema contract. The first ownership/session/project/storage subset is now implemented; see the [foundation implementation record](05-foundation-implementation.md) for installed migrations, adapters and limitations. The remaining entities and invariants are planned. Baseline and scope are in the [index](README.md).

## Ownership and conventions

Use application-generated UUID primary keys, `timestamptz` for UTC instants, `jsonb` for schema-validated structured payloads, and `numeric(20,8)` for monetary accounting. Store currency explicitly. Business time zones remain IANA names; never infer them from the server clock. Hashes use SHA-256 with the canonicalization/version recorded.

Every project child row carries `tenant_id uuid NOT NULL` and `project_id uuid NOT NULL`. References carry both scope columns as well as the referenced ID. Each referenced project-child table declares `UNIQUE (tenant_id, project_id, id)`. This prevents a child row from referencing an object in another project, even within the same tenant. `projects` is the tenant-owned root with `UNIQUE (tenant_id, id)` and no redundant `project_id`; tenant-only records use the same tenant/ID scope. Global `users` and `tenants` have neither child-scope column. Project names and URL slugs are presentation data; IDs establish ownership.

Authenticate users through an OIDC adapter. A verified issuer/subject maps to a local user. Tenant owners/admins manage membership; explicit project membership grants editor, reviewer, publisher or viewer permissions. Editors create candidates, reviewers approve evidence/design, and publishers activate approved deployments. One user may hold several permissions. Public production readers receive only published artifacts and permitted public facts; they do not gain a general tenant session.

Validate issuer/audience/signatures and OAuth state/PKCE, use expiring server-managed sessions with Secure/HttpOnly cookies and explicit CSRF/origin protection, and recheck membership after revocation. Trust forwarding headers only from the configured proxy chain. Quotas use authenticated actor/project identity and verified network identity rather than arbitrary client-supplied forwarded addresses.

New project APIs authorize membership server-side on every read/write before resolving any client-supplied ID. Signed download/preview grants are narrow, expiring and project/build scoped. Shared `STUDIO_ACCESS_TOKEN` remains a legacy/local administrative control during migration and does not establish customer ownership.

Use a non-owner, non-superuser database role with no `BYPASSRLS`, tenant/project authorization in the service layer, and row-level security as a second boundary. Set request scope with transaction-local settings after session authorization; pooled connections must not retain scope. Public serving and worker roles have separate, limited operations. PostgreSQL documents owner/superuser bypass behavior, so enabling RLS alone is insufficient. See [row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

## Table contracts

Unless listed otherwise, tables have `id uuid PRIMARY KEY`, scope columns above, `created_at timestamptz NOT NULL`, and immutable references use restrictive deletion. Mutable entities also have `updated_at` and `revision bigint` for optimistic concurrency. Timestamp columns ending in `_at` use `timestamptz`; all FK columns below are UUIDs. Optional fields are explicitly labelled `NULL`; other listed fields are required. Large text, binary media, source projects and bundles live in object storage.

## PostgreSQL integrity patterns

These fragments demonstrate required migration patterns. They are not a complete runnable migration; referenced tables and security roles must be created in dependency order during implementation.

```sql
-- Every scoped child uses this pattern, not an unscoped id-only FK.
ALTER TABLE builds
  ADD CONSTRAINT builds_scoped_identity UNIQUE (tenant_id, project_id, id),
  ADD CONSTRAINT builds_alternative_fk
    FOREIGN KEY (tenant_id, project_id, alternative_id)
    REFERENCES design_alternatives (tenant_id, project_id, id),
  ADD CONSTRAINT builds_blueprint_fk
    FOREIGN KEY (tenant_id, project_id, blueprint_revision_id)
    REFERENCES blueprint_revisions (tenant_id, project_id, id);

ALTER TABLE design_alternatives
  ADD CONSTRAINT alternatives_slot CHECK (slot BETWEEN 1 AND 3),
  ADD CONSTRAINT alternatives_project_slot UNIQUE (tenant_id, project_id, slot);

CREATE UNIQUE INDEX build_page_membership
  ON build_pages (tenant_id, project_id, build_id, blueprint_page_id);
CREATE UNIQUE INDEX job_deduplication
  ON jobs (tenant_id, project_id, idempotency_key);
CREATE UNIQUE INDEX one_channel_reference
  ON publication_channels (tenant_id, project_id, name);
CREATE UNIQUE INDEX one_build_seal
  ON build_seals (tenant_id, project_id, build_id);

ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
ALTER TABLE projects FORCE ROW LEVEL SECURITY;
CREATE POLICY projects_authorized_scope ON projects
  USING (
    tenant_id = NULLIF(current_setting('everonn.tenant_id', true), '')::uuid
    AND id = NULLIF(current_setting('everonn.project_id', true), '')::uuid
  )
  WITH CHECK (
    tenant_id = NULLIF(current_setting('everonn.tenant_id', true), '')::uuid
    AND id = NULLIF(current_setting('everonn.project_id', true), '')::uuid
  );
```

The example assumes membership has been checked by the trusted service before setting either scope. It covers one project at a time. Authorized project listing/creation and tenant administration require separately reviewed policies or narrow functions; they must not disable isolation. Apply scoped policies to every project-owned table. Application roles cannot select an arbitrary scope using user-supplied connection parameters or SQL.

Constraints/triggers additionally enforce:

- The build's snapshot/fact set match its approved blueprint; its immutable request artifact/hash preserves the generation brief or exact refinement request; the fact set itself refers to that snapshot. Config feature references belong to the same project.
- Starting builds locks the approved blueprint under a SQL transaction. A racing blueprint edit/approval either wins before the lock or creates a new revision; it cannot modify requirements in use.
- Fact-set, snapshot and blueprint membership/content reject updates/deletes once approved/sealed. Fixed build input columns reject updates from insertion. Child artifacts/membership reject changes after a `build_seals` row exists.
- Publication references a ready deployment from the same project, with matching build seal, applicable gate evaluation and unrevoked approval. Arbitrary pointer writes are denied; use the publication service transaction.
- A criterion's target, mapped capture and test evidence agree with their build/blueprint, including references represented inside validated JSON or arrays. Parent builds belong to the same alternative. Test/gate deployment IDs, artifact seals and runtime-binding hashes agree; preview evidence cannot qualify a different production binding.
- State values, hash encoding, route normalization, monetary non-negativity, unique criteria and notification target constraints receive checks. `updated_at` alone is not a concurrency guard.

Indexes begin with tenant/project scope and cover snapshot membership, source-to-target mapping, runnable jobs `(state, not_before)`, lease expiry, test-result lookup, alternative build history and publication history. Use DB migrations with expand/contract changes; do not let generated customer code create or migrate the control-plane schema.

## Immutable evidence and object storage

`page_captures` records raw response bytes and optional rendered DOM separately. Store capture start/end times, status, final/canonical URLs, normalized content units and extractor version. Record missing images, unsupported documents, truncation and failed browser rendering. Limit sizes explicitly; full-source capture means all permitted captured evidence within disclosed limits, not unlimited downloads.

Finalize a snapshot by writing and hashing an ordered manifest of URL outcomes, capture IDs/hashes, scope, coverage, timestamps and extractor configuration. Freeze membership after verifying every referenced object. This preserves consistent inputs while exposing the collection interval. A recrawl creates a new snapshot and change report; it never refreshes an existing snapshot in place. Imported browser evidence is untrusted and must be validated and labelled.

Object keys are scoped and immutable, for example:

```text
tenants/{tenantId}/projects/{projectId}/captures/{captureId}/{sha256}/response.html
tenants/{tenantId}/projects/{projectId}/snapshots/{snapshotId}/{sha256}/manifest.json
tenants/{tenantId}/projects/{projectId}/builds/{buildId}/{sha256}/source.tar
tenants/{tenantId}/projects/{projectId}/builds/{buildId}/{sha256}/output.tar
tenants/{tenantId}/projects/{projectId}/evidence/{testRunId}/{sha256}/mobile.png
```

Upload to a fresh staging key, calculate the hash independently of storage ETags, verify size/checksum/readability, then register the available object and domain reference in SQL. SQL and storage do not share a transaction: unregistered uploads are orphan candidates; unavailable objects prevent sealing/publication. Conditional create and bucket policy protect approved keys against overwrite; test the selected S3-compatible provider's semantics. [S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html) supply a reference mechanism, not a guarantee for every compatible vendor.

Private source/evidence buckets require authorization before issuing short-lived URLs. Preview outputs are read-only and isolated from the studio origin; production exposes only selected website assets. Retain license/attribution/owner-rights evidence for assets. Re-host only when permitted. Required external assets need stable approved URLs and integrity/availability evidence; externally mutable resources weaken reproducibility and must be disclosed.

Object garbage collection checks SQL reachability plus staging age; it never deletes artifacts referenced by active publications or retained rollback deployments. Tenant removal and privacy requests have a separate audited retention process. Encrypt transport/storage, back up database plus referenced objects, and verify restore consistency. Exact retention/RPO/RTO values are deployment decisions recorded before production.

Hosting-specific settings and secret-manager bindings belong to the deployment adapter contract. None is browser-public except explicitly approved public origin metadata.

Retain existing provider configuration (`WEBSITE_PROVIDER`, `OPENROUTER_API_KEY`, `OPENROUTER_MODELS`, `GEMINI_API_KEY`, `GEMINI_WEBSITE_MODELS`, `PEXELS_API_KEY`, ElevenLabs settings and Google OAuth settings). Existing filesystem paths and `CREDENTIAL_ENCRYPTION_KEY` remain necessary for legacy import until migration completes. New credentials should use managed secret references; values never enter blueprint/configuration hashes, manifests, prompts, job payloads or Markdown memory.

## Migration and required verification

1. Introduce ownership and project IDs without changing legacy serving. Import operations require authenticated administrator/owner mapping; never infer ownership from a business name, slug or possession of a crawl UUID.
2. Import `data/crawls` and `data/generated-sites` through their existing validators. Hash/upload readable artifacts, record missing evidence and mark imported builds `legacy_html` with unverified gates. Import failure leaves the old files usable.
3. Import integration settings into a project/environment connection only with explicit owner mapping. Reauthorize OAuth where needed; do not expose decrypted legacy tokens in migration logs.
4. Keep explicit legacy URL-to-project/alternative/build mappings. A mapped URL reads a frozen imported artifact; new generation uses project/build endpoints and does not replace that mapping implicitly.
5. Cut over persistence after scope, migration and restore tests pass. Preserve old data until references and rollback/read behavior have been checked. Legacy availability is not certification under the new gates.

Required implementation checks include cross-tenant and same-tenant cross-project FK rejection, unauthorized object downloads, pooled-scope reset, blueprint/build immutability, two writers racing, interrupted uploads, corrupted/hash-mismatched objects, duplicate migration runs, private-data retention and restore of an active publication. This document records required future checks, not checks already executed.
